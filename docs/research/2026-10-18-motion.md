- **AndroidX `compose/material3`**: commit [`9a589fa`](https://github.com/androidx/androidx/tree/9a589fa61f8661e0cbef9123dcc98d3c1f655fc7/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3) (2026-10-16), shortened to "Compose" below.
- **Material Web**: commit [`60c3e53`](https://github.com/material-components/material-web/tree/60c3e5377ea15d0c6e3b8e3d6bac90889063ebbf) (2026-10-16), shortened to "MW".
- **MDC-Android**: `master`.

Browser targets are those of stack §7: Chrome 153+, Firefox 156+, Safari 26.6+.

**Summary: the changes that would most improve how the app feels, ranked**

1. **Give overlays an enter and an exit.** `Modal` currently pops in and out (`modal.tsx:19-25`). Phones get a bottom sheet that slides up (emphasized-decelerate, 400 ms) and down (emphasized-accelerate, 200 ms). Larger windows get MW's dialog motion: drop 50 px plus a container that grows from 35% height, 500 ms emphasized, closing in 150 ms. The scrim fades. RAC already waits for the animations (§4.1).
2. **Animate navigation.** Use an M3 *top level* fade-through between Clippings, Tags and Settings, and *forward/backward* plus a *container transform* for list → detail (design §8). Replace the skeleton → content pop with a Suspense crossfade. Today every route change is a jump cut, and M3 says "jump cuts should generally be avoided" ([applying transitions](https://m3.material.io/styles/motion/transitions/applying-transitions)).
3. **Make selection indicators move instead of blink.** The tab underline becomes RAC `SelectionIndicator` sliding on the default spatial spring. The nav pill grows from its centre. The segmented/palette check icon pops in (Compose: fade on default effects + scale from 0 on fast spatial). Container colours change on the effects springs. Today all of these toggle `display` or colour instantly (`tabs.tsx:46`, `nav-link.tsx:35-41`, `segmented-buttons.tsx:57-61`).
4. **Use MW's state-layer and focus-ring timing.**
   - Hover: 15 ms linear.
   - Press: fades in over 105 ms and out over 375 ms. Today both directions take 100 ms on the standard curve.
   - Focus ring: grows to 8 px, then settles at 3 px over 600 ms.
   - Fix the sticky `:hover` state layer that stays lit after a tap on touch screens.
5. **Animate the disclosure.** Transition RAC's `--disclosure-panel-height` (provided, unused), and rotate the chevron on a spring. Today the panel and chevron jump (`disclosure.tsx:31,35`).
6. **Make list changes continuous.**
   - A deleted row collapses, and Undo brings it back, with per-row `<ViewTransition>` and the hide inside `startTransition`. Today the row vanishes and its neighbours jump (`clipping-list.tsx:107-111`).
   - Pending → ready crossfades.
   - Toasts enter with fade plus scale 0.8 → 1, as Compose's snackbar does.
7. **Complete the motion tokens.**
   - Emit all six springs for both schemes.
   - Express *emphasized* as a `linear()` path, which corrects design §9.1's "CSS can't express it".
   - Map durations into Tailwind's `--transition-duration-*`, so springs always pair with their duration.
   - Override Tailwind's `--default-transition-*`, which currently gives any `transition` class Tailwind's `cubic-bezier(0.4,0,0.2,1)` 150 ms rather than M3's curve.
8. **Rewrite reduced motion.** The global rule in `base.css:61-69` sets every transition to 1 ms, so it also kills opacity and colour fades, despite its comment and despite M3 ("use subtle fades instead") and WCAG 2.3.3 (opacity and colour are not "motion animation"). Zero only *spatial* durations, through a token.
9. **Replace the progress bar sweep.** The current bar uses the standard (decelerating) curve over 1.5 s, so it slows almost to a stop and then jumps back (`theme.css:225-240`). Use MW/Compose's two-line indeterminate motion: transform only, 1.75–2 s.
10. **Tone down the theme switch.** Keep the circular reveal for light/dark only. Palette and contrast get a short crossfade, and a failed-save revert gets no animation (`appearance-settings.tsx:50-57`).

No new dependency is needed: CSS, RAC's entering/exiting states and React `<ViewTransition>` cover all of the above (§4.5).

## 2. M3 motion system

### 2.1 Two systems: springs for components, easing and duration for transitions

- **Springs replace easing and duration.** "The physics system is replacing the previous system based on easing and duration" ([how it works](https://m3.material.io/styles/motion/overview/how-it-works), May 2025). But the easing/duration page says it "is still used for transitions" and is "no longer maintained" ([applying easing](https://m3.material.io/styles/motion/easing-and-duration/applying-easing-and-duration)). The transitions pages agree: "M3 transitions use the legacy easing and duration system" ([transition patterns](https://m3.material.io/styles/motion/transitions/transition-patterns)).
  - So **components** (state changes, indicators, small enters) use **springs**.
  - **Screen and overlay transitions** use **easing and duration**.
- **Schemes.** "Expressive is Material's opinionated motion scheme, and should be used for most situations"; "Standard feels more functional with minimal bounce, and should be used for utilitarian products" ([how it works](https://m3.material.io/styles/motion/overview/how-it-works)).
  - Compose's plain `MaterialTheme` defaults to `standard()` ([MaterialTheme.kt:181](https://github.com/androidx/androidx/blob/9a589fa61f8661e0cbef9123dcc98d3c1f655fc7/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/MaterialTheme.kt#L181)).
  - `MaterialExpressiveTheme` defaults to `expressive()` ([:262](https://github.com/androidx/androidx/blob/9a589fa61f8661e0cbef9123dcc98d3c1f655fc7/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/MaterialTheme.kt#L262)).
  - KDoc: standard is "for utilitarian UI elements and recurring interactions", expressive "for prominent UI elements and hero interactions" ([MotionScheme.kt:117-132](https://github.com/androidx/androidx/blob/9a589fa61f8661e0cbef9123dcc98d3c1f655fc7/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/MotionScheme.kt#L117-L132)).
  - M3 allows "swap the default motion scheme per element" (Level 3).
- **Token shape.** The token is `md.sys.motion.spring.{fast|default|slow}.{spatial|effects}`; the scheme "isn't part of the token itself… it's called at the product level" (how it works).
  - **Spatial** is for "x and y position, rotation, size, rounded corners" and "overshoots the final value".
  - **Effects** is for "color and opacity… where there shouldn't be any overshoot".
  - **Speed**: default for "animations that partially cover the screen", fast for "small components, such as switches and buttons", slow for "full-screen animations".
- **Values.** Damping/stiffness match design §9.1; re-checked today in `StandardMotionTokens.kt`, `ExpressiveMotionTokens.kt` (both `v0_14_0`) and MW's `_md-sys-motion.scss`. The effects springs are identical in both schemes.
- **Emphasized easing.** The emphasized curve is the path `M 0,0 C 0.05,0 0.133333,0.06 0.166666,0.4 C 0.208333,0.82 0.25,1 1,1`. CSS is listed as "N/A (Use Standard as a fallback)" ([tokens & specs](https://m3.material.io/styles/motion/easing-and-duration/tokens-specs)). With `linear()` and explicit input stops ([MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/easing-function/linear)) the path samples to under 0.9% error, dense where it is steep:

```css
--md-sys-motion-easing-emphasized: linear(0, 0.003 2%, 0.013 4%, 0.03 6%, 0.056 8%, 0.093 10%, 0.146 12%, 0.222 14%, 0.305 15.5%, 0.4 16.67%, 0.52 18%, 0.636 20%, 0.706 22%, 0.773 25%, 0.84 30%, 0.883 35%, 0.912 40%, 0.951 50%, 0.973 60%, 0.987 70%, 0.995 80%, 0.999 90%, 1);
```

- **Easing pairs.** M3's suggested easing and duration pairs ([applying easing](https://m3.material.io/styles/motion/easing-and-duration/applying-easing-and-duration)):
  - Emphasized 500 ms: begins and ends on screen.
  - Emphasized-decelerate 400 ms: enters the screen.
  - Emphasized-accelerate 200 ms: exits the screen permanently.
  - The standard set (300 / 250 / 200 ms) is for "small utility focused transitions".
  - Duration scales with the area covered. "Transitions that exit, dismiss, or collapse an element use shorter durations."

### 2.2 Are the repo's `linear()` springs right?

**Yes.** M3 now publishes a cubic-bezier + duration table for the web under "Web: Convert springs to curves" ([specs](https://m3.material.io/styles/motion/overview/specs)), and says to "use springs when possible, otherwise use curves that mimic the springs". I compared the damped-oscillator solution that `springs.ts` uses against that table (script in this session's scratchpad; numbers below):

| Spring | Physics: 50% / 90% / 99% reached at (ms) | M3 web curve: 50 / 90 / 99 (ms) | M3 curve, duration |
|---|---|---|---|
| standard fast spatial (0.9/1400) | 43 / 92 / 138 | 45 / 104 / 179 | `0.27,1.06,0.18,1`, 350 ms |
| standard default spatial (0.9/700) | 61 / 129 / 194 | 64 / 149 / 256 | same curve, 500 ms |
| standard slow spatial (0.9/300) | 92 / 197 / 297 | 95 / 223 / 383 | same curve, 750 ms |
| expressive fast spatial (0.6/800) | 49 / 84 / 97, overshoot 9.5% | 45 / 84 / 97, 9.2% | `0.42,1.67,0.21,0.90`, 350 ms |
| expressive default spatial (0.8/380) | 78 / 153 / 202, 1.5% | 77 / 154 / 203, 1.4% | `0.38,1.21,0.22,1.00`, 500 ms |
| expressive slow spatial (0.8/200) | 107 / 211 / 278, 1.5% | 103 / 216 / 276, 1.9% | `0.39,1.29,0.35,0.98`, 650 ms |
| fast / default / slow effects (1.0/3800, 1600, 800) | 28/64/108, 42/98/166, 60/138/235 | 26/64/106, 42/99/157, 59/138/225 | 150 / 200 / 300 ms |

- **Expressive springs and effects.** These match M3's own conversions almost exactly.
- **Standard spatial.** M3 uses one curve stretched over 350/500/750 ms. Most of its motion lands at the same times as the physics; it just carries a longer tail.
- **Settle times.** The repo's settle times (cut at 0.2%) are 156 / 220 / 335 ms for standard spatial and 138 / 212 / 300 ms for effects.
- **Corrections.**
  - Design §9.2's caveat that the curves are "my numerical approximation, not M3-published" can now be closed: M3 publishes curves for the web, and the repo's are within a few percent of them.
  - The `linear()` form is *better* than M3's bezier for the expressive fast spring, whose bezier ends at y = 0.90 and has to jump.
- **Keep `linear()`, and:**
  - Emit all six tokens per scheme. The effects tokens are shared between schemes.
  - Use 40 stops for the expressive spatial springs (max error 2.2% → 0.6%).
  - Bake in the reduced-motion factor (§5.2).
- **Interruption.** Interrupting a `linear()` or `cubic-bezier` transition restarts the curve from zero velocity; real springs keep their velocity. M3 notes springs "handle gestures, interruptions, and retargeting" (how it works). The only interruptible case in Clippings is a fast hover/press toggle, which is fine on the web. This is the one real gap a JS spring library would close (§4.5).

Rule of thumb from this table: **anything that moves or resizes uses the spatial springs; anything that changes colour or opacity uses effects. Small components get *fast*, panes get *default*.**

### 2.4 Which scheme for Clippings

- **Option A** (design §9's choice): standard scheme as the product default, and expressive only for hero moments (the "saved" check, the chip-add pop). M3 sanctions this both as "Standard… for utilitarian products" and as "Level 3: swap per element".
- **Option B**: expressive as the default, as M3 recommends "for most situations".
- **Recommendation**: keep A. Clippings is a calm reading tool on a paper look.
  - Generate **both** schemes and select them through one indirection (§5.1), as M3 does at product level, so B is a one-line change.
  - Compose's button morph uses effects even in the expressive scheme, so either way buttons don't bounce.
  - "Common transitions should not use overt style effects like bouncy springs" ([applying transitions](https://m3.material.io/styles/motion/transitions/applying-transitions)). So screen transitions stay on emphasized easing in both options.

## 3. Transitions and component motion

### 3.1 M3 transition patterns, mapped to Clippings flows

M3's current pattern names ([transition patterns](https://m3.material.io/styles/motion/transitions/transition-patterns)) are container transform, forward and backward, lateral, top level, enter and exit, and skeleton loaders. The MDC-era names map onto them:
- **Shared axis** ([MaterialSharedAxis.java](https://github.com/material-components/material-components-android/blob/master/lib/java/com/google/android/material/transition/MaterialSharedAxis.java)): 30 dp slide plus fade-through, `motionDurationLong1` (450 ms) emphasized. It is the Android **forward/backward**.
- **Fade through** ([MaterialFadeThrough.java](https://github.com/material-components/material-components-android/blob/master/lib/java/com/google/android/material/transition/MaterialFadeThrough.java)): the old screen fades out over the first 35% ([FadeThroughProvider.java](https://github.com/material-components/material-components-android/blob/master/lib/java/com/google/android/material/transition/FadeThroughProvider.java)). The new one fades in over the remaining 65% while scaling 0.92 → 1, long1 emphasized. It is the **top level** pattern.
- **Container transform**: enter `motionDurationLong2` (500 ms), return `medium4` (400 ms), emphasized ([MaterialContainerTransform.java](https://github.com/material-components/material-components-android/blob/master/lib/java/com/google/android/material/transition/MaterialContainerTransform.java)). Slide distance is 30 dp (`mtrl_transition_shared_axis_slide_distance`).

### 3.4 Buttons, selection controls, disclosure, progress

- **Button press morph (Expressive).**
  - Compose: pressed shape is corner-small (8 dp) for XS/S buttons (32/40 dp) and corner-medium (12 dp) for M (56 dp). The resting shape is corner-full.
  - It animates on **default effects**, not spatial ([ButtonSmallTokens.kt](https://github.com/androidx/androidx/blob/9a589fa61f8661e0cbef9123dcc98d3c1f655fc7/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/tokens/ButtonSmallTokens.kt#L45-L46), Button.kt above).
  - The repo's 48 px button falls between S and M. Use 8 px (`--radius-sm`) or 12 px (`--radius-md`); a matter of taste.
  - **Pitfall**: `--radius-full` is `9999px`. Interpolating 9999 px → 8 px stays visually round for about 99% of the animation and then snaps. Transition from half the height (24 px) instead.
  - Reduced motion: "Disable decorative effects like… shape morphing" ([applying transitions](https://m3.material.io/styles/motion/transitions/applying-transitions)), so there should be no shape change at all, not just an instant one.
- **Tabs.**
  - Use RAC's `SelectionIndicator`. RAC's docs use `transition-property: translate, width` and turn it off under reduced motion ([Tabs](https://react-aria.adobe.com/Tabs)).
  - MW animates its indicator for 250 ms emphasized with FLIP `translateX` + `scaleX`, and fades it instead under reduced motion ([tab.ts:140-190](https://github.com/material-components/material-web/blob/60c3e5377ea15d0c6e3b8e3d6bac90889063ebbf/tabs/internal/tab.ts#L140-L190)).
  - Recommended: the default spatial spring, as Compose does.
  - Animating `width` is a layout property, but on one 3 px element in its own positioned box it is cheap.
  - Reduced motion: let it jump, but fade it in.
- **Nav indicator.** Compose animates width = full × progress and alpha = progress. In CSS, `clip-path: inset(0 50% round …) → inset(0 round …)` keeps the pill's round ends. `scaleX` would squash the corners mid-animation.
- **Disclosure.** RAC's docs: `height: var(--disclosure-panel-height); transition: height 250ms; overflow: clip`, with the chevron `rotate` transitioning over 200 ms ([Disclosure](https://react-aria.adobe.com/Disclosure)).
  - Use the default spatial spring for height and fast spatial for rotation.
  - `interpolate-size` / `calc-size()` would let `height: auto` animate without JS, but they are Chrome 129+ only. Firefox and Safari have neither (BCD 8.1.6). RAC's px variable makes them unnecessary.
  - `hidden="until-found"`, which RAC uses so find-in-page can open the panel, is now in all targets: Chrome 102, Firefox 148, Safari 26.2 (BCD).
- **Progress, indeterminate.**
  - Compose: a 1750 ms cycle with two lines. Line 1's head moves over 0–1000 ms and its tail over 250–1250 ms; line 2's head over 650–1500 ms and its tail over 900–1750 ms. Each segment is emphasized-accelerate. There is a 4 dp gap to the track (Expressive) and a stop indicator (ProgressIndicator.kt above).
  - MW does it with transforms only (two bars × translate and scaleX keyframes, 2 s, inherited from MDC).
  - Port MW's keyframes (Apache-2.0; link in A11) rather than animating `left`/`right` or `@property` insets, which run on the main thread. That matters because the bar runs while the list is busy loading.

## 4. Implementing on this stack

### 4.1 React Aria Components

- **States.** "`data-entering` represents the starting state of the entry animation". With CSS transitions it "is only applied for one frame", so the transition goes on the default state. "`data-exiting` represents the ending state of the exit animation", and the element waits "for any animations to complete before being removed from the DOM" ([styling](https://react-aria.adobe.com/styling)). Keyframe animations work too but "are not interruptible".
- **How RAC waits** (read in `react-aria/dist/private/utils/animation.mjs`):
  - `useEnterAnimation`: while the element is not ready (for example, a popover before it has been positioned), RAC hides it with `opacity: 0` and `clip-path: inset(50%)`. When the enter state starts, it cancels stray `CSSTransition`s.
  - `useExitAnimation`: collects `element.getAnimations()` that are *running* on a document timeline, awaits `finished`, then unmounts in `flushSync`.
  - Only the element's **own** animations count, not its subtree. Children must finish within the parent's animation.
  - `onEnter`/`onExit` may return a promise, for JS animations ([Modal](https://react-aria.adobe.com/Modal)).
  - `Modal` tracks both the overlay and the modal element (`Modal.mjs:96-99`). `Dialog` "waits to move focus until the modal has entered" (`:122`).
- **Who supports entering/exiting.** `Popover`, `Modal`/`ModalOverlay`, `Tooltip`, `TabPanel`, and collection items in GridList, ListBox, Menu, Table, Tree and TagGroup (via `useEnterAnimation`/`useExitAnimation` imports in RAC 1.22.1). Toast does not.
- **SelectionIndicator / SharedElement.**
  - On unmount it snapshots the rect and the computed values of every property in the element's `transition-property`.
  - The new instance starts from the old values (`translate` as a FLIP delta) and moves to its own a frame later.
  - Only listed transition properties animate: put `translate`, `width` (or `clip-path`) and colours in `transition-property`.
  - Used by Tabs, ToggleButtonGroup, RadioGroup, GridList, ListBox, Menu, TagGroup, Table and Tree (`SharedElementTransition.mjs`).
- **Tailwind.** v4 has native `data-entering:` / `data-exiting:` (boolean data-attribute variants, as the repo already uses for `data-selected:`), `starting:` (= `@starting-style`), `motion-safe:` and `transition-discrete` (`tailwindcss/dist/lib.js`). Two constraints:
  - The repo's lint bans arbitrary values (`shadcn/no-arbitrary-values` in `.oxlintrc.json`), so `transition-[translate,width]` and `h-(--disclosure-panel-height)` are out. Put multi-property motion in `@utility` blocks in `packages/ui` (§5).
  - Only `--transition-duration-*` theme keys give named `duration-*` classes (`valueThemeKeys: ["--transition-duration"]` in Tailwind's source).

### 4.3 View transitions in React 19.3 / Next 16.4

Stack §8 settled the platform. What matters for motion:
- **What activates them.** Only Transitions, `<Suspense>` and `useDeferredValue` activate `<ViewTransition>`; plain `setState` doesn't ([React](https://react.dev/reference/react/ViewTransition)). In Next, "route navigations are transitions" ([guide](https://nextjs.org/docs/app/guides/view-transitions)). Row delete (A24) must therefore call `hide` inside `startTransition`.
- **Wrapper placement.** Wrap each `page.tsx`, not the layout ("Layouts persist across navigations, so enter and exit never fire there").
- **`default="none"`.** Add it on every typed wrapper, or every named element crossfades on unrelated transitions.
- **Keep the page clickable.** Add `::view-transition { pointer-events: none }`. Named participants still aren't hit-testable during the transition, so keep transitions short.
- **Manual transitions.** "If you have something else on the page running a ViewTransition React will interrupt it" (React). This affects `transitionAppearance` and a toast `wrapUpdate`. Both are short and rarely coincide with navigation. Delete is the exception: it navigates (`router.push('/')`) and adds a toast in the same tick, so put the toast's enter on `@starting-style`, not a view transition.
- **Reduced motion.** "React doesn't automatically disable animations" (React). Next's guide zeroes all durations. Chrome's guide prefers subtler motion: "'reduced motion' doesn't mean the user wants _no motion_" ([Chrome](https://developer.chrome.com/docs/web-platform/view-transitions/same-document)). Use the M3 approach: keep crossfades and drop the slides and morph geometry (§5.2).

### 4.5 Is a JS animation library worth it?

- **Motion's cost** ([reduce bundle size](https://motion.dev/docs/react-reduce-bundle-size)):
  - The `motion` component costs about 43 kb.
  - `m` + `LazyMotion` costs "just over 5kb" plus 24 kb (`domAnimation`) or 38 kb (`domMax`, which includes layout animations and drag).
  - `useAnimate` mini costs 3.3 kb.
- **What it would buy**: velocity-preserving interruptible springs, and gesture-driven motion such as drag-to-dismiss.
- **Clippings needs neither.**
  - RAC `Sheet` uses native scrolling (design §9.3).
  - Hover/press interruptions are short.
  - Layout and reorder animation is covered by `<ViewTransition>`.
- **Recommendation: no new dependency.** Revisit only if a drag gesture appears.

### 5.2 Reduced motion (replaces `base.css:60-69`)

- **Spatial springs**: `--md-sys-motion-spatial-factor: 0` makes every spatial-spring transition instant while effects still fade.
- **Easing-based movement**: the dialog, sheet and view-transition slides each carry an explicit `@media (prefers-reduced-motion: reduce)` override that swaps to a short fade (snippets below and in §4.4).
- **Global rule**: keep `scroll-behavior: auto`; drop the 1 ms `!important` net.
  - If a safety net is still wanted for third-party CSS, limit it to `animation-iteration-count: 1` plus pausing infinite decoration. Never transitions.
- **Shape morph**: wrap the button's pressed shape in `motion-safe:`.
- **Already correct**: the progress bar parks under reduced motion, and the theme switch already crossfades.

**Performance notes**:
- Prefer `opacity`, `transform`/`translate`/`scale`/`rotate` and `clip-path`. "Avoid any property that triggers layout or paint unless it's absolutely necessary" ([web.dev animations guide](https://web.dev/articles/animations-guide)). The only layout animations above are the disclosure and tab-panel heights, in small `overflow: clip` boxes. This is what RAC's docs do.
- **Don't add `will-change` preemptively**: "Use the `will-change` property sparingly, and only if you encounter a performance issue" (web.dev).
- **Theme switch cost**: during a view transition's update callback "the page is frozen" ([Chrome](https://developer.chrome.com/docs/web-platform/view-transitions/same-document)). `transitionAppearance` already keeps the update to `flushSync` + attribute changes. The full-page style recalculation that a palette change causes is the real INP cost, and it exists with or without animation.
- **INP impact**: CSS transitions and animations on compositor properties don't occupy the main thread, so none of §5.3 adds to INP. RAC's `flushSync` on exit-animation end is one small synchronous render.

## 7. Corrections to earlier research

- **Design §9.1**: "emphasized … the real emphasized curve is a path, which CSS can't express". It can, with `linear()` (§2.1).
- **Design §9.2**: "This is my calculation, not an M3 artifact". M3 now publishes web curves for every spring, and the repo's `linear()` versions match them to within a few percent (§2.2). Keep `linear()`.
- **Design §9.3, dialog "fade + scale .96 → 1"**: M3 avoids scale for within-bounds enters (§3.1). Use MW's y-axis drop + container grow.
- **Design §9.3, "Skeletons: static (no shimmer)"**: M3 skeletons have "a subtle pulsing animation" ([transition patterns](https://m3.material.io/styles/motion/transitions/transition-patterns#skeleton-loaders)). A slow opacity pulse is M3 and reduced-motion safe.
- **Design §9.3, disclosure via `grid-template-rows: 0fr → 1fr`**: RAC 1.22 already provides `--disclosure-panel-height` in px and waits for the animation before hiding. Use that instead.
- **Design §9.3, reduced motion "a global… 1ms… Keep opacity fades"**: these contradict each other. The global rule removes the fades (A9).
- **Design §9.3, "standard M3 motion scheme throughout"**: M3 now calls expressive the default recommendation and standard the utilitarian option. Standard remains a valid, documented choice (§2.4).

## Unverified / open questions

- **Browser back.** React says popstate navigations skip animations ([React](https://react.dev/reference/react/ViewTransition): "animations won't run for the back button… upgrade your router to use the Navigation API"). Next's guide says the morph "still applies" on browser back ([guide](https://nextjs.org/docs/app/guides/view-transitions)). Whether Next 16.4's router uses the Navigation API was not checked. Test in each browser.
- **`<ViewTransition>` inside RAC `GridList`.** Wrapping `GridListItem` in `<ViewTransition>` may interfere with RAC's collection builder. Not tested.
- **Toast and theme-switch interruptions.** Interaction between `ToastQueue({wrapUpdate})`, `transitionAppearance` and React-driven view transitions: React says it interrupts other view transitions. Carried over from design research; still not prototyped.
- **Compositor support.** Whether `clip-path` animations (dialog grow, nav pill) run on the compositor in all three engines. They are at worst paint-only, but not confirmed off-main-thread.
- **Tailwind default override.** Tailwind 4.3.3 honouring `--default-transition-duration` / `--default-transition-timing-function` overridden inside `@theme inline` was read from the source (`e.resolve(null, ["--default-transition-timing-function"])`), not run.
- **Snackbar guidance vs code.** M3's guideline says Android components avoid scale on enter and "expand… along the x or y axis" ([transition patterns](https://m3.material.io/styles/motion/transitions/transition-patterns#enter-and-exit)). Compose's snackbar, menu and tooltip nevertheless scale from 0.8. This file follows the code for small surfaces and the guideline for the dialog.
- **Spring-token tables on the M3 site.** The token tables on [specs](https://m3.material.io/styles/motion/overview/specs) and [tokens & specs](https://m3.material.io/styles/motion/easing-and-duration/tokens-specs) are an interactive widget that didn't render as text. Spring values come from Compose and MW sources instead, which agree with each other.
- **Device-specific springs.** M3 says spring values "differ depending on if the device is a wearable, phone, or tablet" (how it works). No web or desktop values are published; the phone values are used.
- **Button morph on the web.** Whether M3 intends the Expressive press morph for web buttons.
  - MW's generated tokens at `60c3e53` do carry it: `md.comp.button.pressed.container.shape` = corner-small for the 40 px button ([_md-comp-button.scss:102-103](https://github.com/material-components/material-web/blob/60c3e5377ea15d0c6e3b8e3d6bac90889063ebbf/tokens/versions/latest/sass/_md-comp-button.scss#L102-L103)), and corner-medium for the 56 px one.
  - MW's `button/internal` styles don't use these tokens.
- **Ripple vs. press fade.** The ripple's value over the improved press fade is a matter of taste. Try the press-timing change alone first.
- **Scheme choice.** Option A or B in §2.4 is a product decision for the user.
